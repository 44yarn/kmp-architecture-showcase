# kotlin-inject DI Migration — PoC Report

[Japanese / 日本語](kotlin-inject-migration-ja.md)

## Overview

This branch migrates the project's DI from **Hilt (Android) + Koin (iOS)** dual setup to **kotlin-inject 0.9.0 + kotlin-inject-anvil 0.1.7** (KMP unified, compile-time graph validation via KSP).

kotlin-inject is a compile-time dependency injection framework for Kotlin by [Eva Tatarka](https://github.com/evant/kotlin-inject). kotlin-inject-anvil is an extension by [Amazon](https://github.com/amzn/kotlin-inject-anvil) that adds cross-module contribution merging (`@ContributesTo`, `@MergeComponent`).

### Why not merged?

This PR is kept open as a reference implementation alongside the Metro PoC (`feature/metro-di-poc`), comparing two KMP DI approaches.

**Merge conditions:**
- Decide between kotlin-inject-anvil and Metro based on ecosystem maturity
- iOS cross-module `@MergeComponent` support (currently requires inline fallback)
- Team alignment on DI strategy

## Key Findings

### 1. Android cross-module `@ContributesTo` + `@MergeComponent` works perfectly

kotlin-inject-anvil's `@ContributesTo` contributions declared in `core/data`, `feature/login`, and `feature/home` are automatically merged into `ShowcaseAppComponent` (`@MergeComponent`) in the `app` module. This is the **key advantage over Metro 0.10.4**, where cross-module `@ContributesTo` failed with `IR_EXTERNAL_DECLARATION_STUB`.

The generated `KotlinInjectShowcaseAppComponentMerged` interface correctly inherits all contributions:
```kotlin
public interface KotlinInjectShowcaseAppComponentMerged :
    IoGithubYarn44KmpShowcaseFeatureLoginDiLoginComponent,
    IoGithubYarn44KmpShowcaseCoreDataDiDataComponent,
    IoGithubYarn44KmpShowcaseFeatureHomeDiHomeComponent,
    IoGithubYarn44KmpShowcaseCoreDataDiAndroidDataStoreComponent
```

### 2. iOS cross-module `@MergeComponent` does NOT work

On iOS targets, `@MergeComponent` generates an **empty merged interface**. The KSP processor cannot discover `@ContributesTo` contributions from other modules' klib outputs.

**Root cause:** KSP's classpath scanning works with JARs (Android/JVM) but not with klibs (Kotlin/Native). The anvil metadata generated by KSP in `core/data` is compiled into a klib, but the KSP processor in `shared` cannot scan it.

**Workaround:** iOS uses plain `@Component` with all `@Provides` inlined — same pattern as the Metro PoC fallback.

**References:**
- [kotlin-inject-anvil Issue #118](https://github.com/amzn/kotlin-inject-anvil/issues/118)
- Android: `@MergeComponent` in `app/` — auto-merges all contributions
- iOS: `@Component` in `shared/iosMain/` — providers inlined manually

### 3. `kspCommonMainMetadata` and `kspIosXxx` must NOT be used simultaneously

Using both configurations causes Redeclaration errors in kotlin-inject-anvil. The correct approach is to use **target-specific KSP only** (`kspAndroid`, `kspIosArm64`, `kspIosSimulatorArm64`, `kspIosX64`).

### 4. `@AssistedFactory` works in commonMain

kotlin-inject 0.8.0+'s `@Assisted` + `@AssistedFactory` annotations work across all KMP targets. `HomeViewModel.Factory` is declared in `commonMain` and works on both Android and iOS.

### 5. `@Inject constructor` does NOT support default arguments (KSP limitation)

Unlike Metro, kotlin-inject cannot see default argument values through KSP. `IndicatorState` and `DialogPresenter` must be provided explicitly via `@Provides` methods rather than using default parameter values.

### 6. `expect/actual` pattern required for `create()` on iOS

KSP generates `IosAppComponent::class.create()` in each iOS target source set (`iosSimulatorArm64Main`, etc.), but this extension is not visible from the `iosMain` intermediate source set. The solution is:
- `iosMain`: `internal expect fun createIosAppComponent(): IosAppComponent`
- Each target: `internal actual fun createIosAppComponent() = IosAppComponent::class.create()`

### 7. Side effects of migration (same as Metro PoC)

- **Single-Activity architecture**: `InfoActivity` and `ActivityLauncher` removed; all screens in one `NavHost`
- **`KmpViewModel` deleted**: ViewModels extend `androidx.lifecycle.ViewModel` directly
- **Android `@HiltViewModel` wrappers eliminated**: `AndroidLoginViewModel` (52 lines) and `AndroidHomeViewModel` (52 lines) deleted

## Architecture After Migration

### Android

```
ShowcaseApplication
  └── appComponent: ShowcaseAppComponent (lazy, @MergeComponent)
        ├── Merges: DataComponent (@ContributesTo from core/data/commonMain)
        ├── Merges: AndroidDataStoreComponent (@ContributesTo from core/data/androidMain)
        ├── Merges: LoginComponent (@ContributesTo from feature/login/commonMain)
        └── Merges: HomeComponent (@ContributesTo from feature/home/commonMain)

MainActivity
  └── setContentWithTheme {
        ShowcaseNavGraph(appComponent = appComponent)
          ├── LoginScreen(viewModel = viewModel { appComponent.loginViewModel })
          ├── HomeScreen(viewModel = viewModel { appComponent.homeViewModelFactory.create(...) })
          └── InfoScreen(onBack = ...)
      }
```

### iOS

```
IosAppComponent (@Component, singleton — inline providers due to klib limitation)
  ├── @Provides fun provideIoDispatcher()
  ├── @Provides fun provideDataStore()
  ├── @Provides fun providePreferenceStorage()
  ├── @Provides fun provideIndicatorState()
  ├── @Provides fun provideDialogPresenter()
  ├── @Provides fun provideSnackbarPresenter()
  ├── val loginViewModel: LoginViewModel
  └── val homeViewModelFactory: HomeViewModel.Factory

Top-level helpers (Swift-facing):
  ├── bootstrapIosAppComponent() → ShowcaseApp.init
  ├── getLoginViewModel()        → LoginView
  └── getHomeViewModel(...)      → HomeView
```

## Comparison with Metro PoC

| Aspect | kotlin-inject-anvil | Metro 0.10.4 |
|--------|-------------------|-------------|
| Android cross-module `@ContributesTo` | **Works** (auto-merge) | Does not work (inline fallback) |
| iOS cross-module `@MergeComponent` | Does not work (klib limitation) | Does not work (IR stub limitation) |
| `@AssistedFactory` | Works (KSP) | Works (compiler plugin) |
| Default arguments in `@Inject` | Not supported (KSP) | **Supported** (IR access) |
| Kotlin version compatibility | Stable (KSP API) | Fragile (compiler plugin ABI) |
| Build speed | Slower (KSP overhead) | **Faster** (compiler plugin) |
| Production adoption | Bitkey (170 modules), Tivi | DroidKaigi 2025 |
| Maturity | 0.9.0 + anvil 0.1.7 | 0.10.4 (pre-1.0) |

**Key takeaway:** kotlin-inject-anvil solves Metro's biggest limitation (Android cross-module) while sharing the same iOS limitation. The trade-off is losing default argument support and slightly slower builds.

## KSP Configuration Notes

### Per-target KSP (required pattern)

Each KMP module that uses kotlin-inject annotations must configure KSP for **every target individually**:

```kotlin
dependencies {
    add("kspAndroid", libs.kotlinInjectCompiler)
    add("kspAndroid", libs.kotlinInjectAnvilCompiler)
    listOf("kspIosX64", "kspIosArm64", "kspIosSimulatorArm64").forEach { config ->
        add(config, libs.kotlinInjectCompiler)
        add(config, libs.kotlinInjectAnvilCompiler)
    }
}
```

Do **not** use `kspCommonMainMetadata` alongside target-specific KSP — this causes Redeclaration errors.

### Convention plugin limitation

The `showcase.primitive.kotlin-inject` convention plugin only applies the KSP Gradle plugin. Runtime dependencies and KSP compiler configurations are added directly in each module's `build.gradle.kts` because `configureKmpOrAndroid`'s `commonMain` block does not correctly add dependencies to KMP sourceSets.
